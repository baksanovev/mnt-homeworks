### Задание 1. Метрики для мониторинга проекта

**Условие:** Необходимо настроить мониторинг платформы, которая выполняет вычисления, формирует текстовые отчёты, сохраняет их на диск и взаимодействует с пользователями по HTTP. Вычисления создают нагрузку на процессор.

**Ответ:**

Для такого проекта я бы выбрал следующие метрики:

| Метрика | Назначение |
|---|---|
| CPU Usage | Мониторинг загрузки процессора во время вычислений |
| Load Average | Контроль общей нагрузки на систему и очереди задач |
| RAM Usage | Контроль использования оперативной памяти |
| Disk Usage | Контроль свободного места для сохранения отчётов |
| Disk I/O | Контроль скорости чтения и записи на диск |
| Inodes | Контроль количества свободных inode файловой системы, необходимых для создания новых файлов и каталогов |
| HTTP Requests | Подсчёт количества запросов к приложению |
| HTTP Response Time | Измерение времени обработки HTTP-запросов |
| HTTP Status Codes | Отслеживание успешных ответов и ошибок HTTP |
| Service Availability | Контроль доступности приложения |

**Вывод:** данный набор метрик позволит контролировать загрузку ресурсов, своевременно выявлять проблемы с дисковым пространством и отслеживать доступность и производительность приложения.

### Задание 2. Мониторинг качества обслуживания

**Условие:** Менеджер продукта хочет понимать качество предоставляемого сервиса и выполнение обязательств перед клиентами, а не технические метрики CPU, RAM и Inodes.

**Ответ:**

Я бы предложил использовать показатели **SLI, SLO и SLA**.

- **SLI (Service Level Indicator)** — измеряемый показатель качества сервиса, например процент успешных запросов.
- **SLO (Service Level Objective)** — целевое значение показателя, например доступность сервиса 99,9%.
- **SLA (Service Level Agreement)** — соглашение с клиентом, определяющее обязательства по качеству обслуживания.

Для менеджера можно создать отдельный Dashboard со следующими показателями:

1. Доступность сервиса в процентах.
2. Процент успешных HTTP-запросов.
3. Среднее время ответа приложения и 95-й перцентиль задержки.
4. Количество ошибок за выбранный период.
5. Количество успешно сформированных отчётов.
6. Выполнение целевого уровня обслуживания (SLO).

**Вывод:** менеджер будет видеть показатели, отражающие качество сервиса с точки зрения клиентов, а технические метрики останутся для инженеров.

**Условие:** Нет финансирования на централизованную систему сбора логов, но разработчикам необходимо получать ошибки своих приложений.

**Вывод:** даже без полноценной системы централизованного логирования можно оперативно информировать разработчиков о возникающих ошибках.

### Задание 4. Ошибка при расчёте SLI для проверки SLA

**Условие:** Мониторинг показывает уровень успешных HTTP-запросов не выше 70%, хотя сервер не возвращает ошибки 4xx и 5xx.

Текущая формула:

```text
summ_2xx_requests / summ_all_requests
```

**Ответ:**

Ошибка заключается в том, что в числителе учитываются только HTTP-ответы категории `2xx`, а в знаменателе — все HTTP-ответы.

При этом сервер может возвращать ответы категории `3xx`, которые обозначают перенаправления.

Например:

- Всего HTTP-запросов: 1000.
- Ответов 2xx: 700.
- Ответов 3xx: 300.
- Ответов 4xx и 5xx: 0.

Результат расчёта:

```text
700 / 1000 * 100% = 70%
```

Таким образом, мониторинг показывает 70%, хотя ошибок 4xx и 5xx нет.

Если в рамках согласованного SLI перенаправления считаются успешными, можно использовать:

```text
(summ_2xx_requests + summ_3xx_requests) / summ_all_requests
```

В этом случае результат составит 100%.

**Вывод:** необходимо корректно определить, какие HTTP-ответы считаются успешными, и учитывать их в формуле SLI. Нельзя автоматически считать любые перенаправления успешными без проверки требований приложения.

### Задание 5. Плюсы и минусы Pull и Push систем мониторинга

**Ответ:**

Существуют две основные модели получения метрик: Pull и Push.

#### Pull-модель

В модели Pull сервер мониторинга самостоятельно обращается к наблюдаемым системам и забирает метрики.

**Преимущества:**

- Централизованное управление сбором метрик.
- Возможность контролировать доступность источников.
- Удобное обнаружение и конфигурирование целей мониторинга.
- Нет необходимости отправлять метрики с каждого сервера самостоятельно.

**Недостатки:**

- Сервер мониторинга должен иметь сетевой доступ к источникам.
- Могут возникать сложности при мониторинге серверов за NAT и межсетевыми экранами.
- Кратковременные процессы могут завершиться до очередного опроса.

Пример: Prometheus.

#### Push-модель

В модели Push источники самостоятельно отправляют метрики в систему мониторинга.

**Преимущества:**

- Подходит для серверов в закрытых сетях, если разрешена исходящая передача данных.
- Удобна для кратковременных задач.
- Источники самостоятельно инициируют отправку данных.

**Недостатки:**

- Сложнее определить, перестал ли источник отправлять данные из-за сбоя.
- Необходимо контролировать нагрузку на приёмник метрик.
- Требуется дополнительная настройка безопасности при приёме данных.

Пример: Telegraf, отправляющий метрики в InfluxDB.

**Вывод:** выбор модели зависит от архитектуры инфраструктуры, сетевых ограничений и требований к мониторингу. На практике часто применяются гибридные решения.

### Задание 6. Классификация систем мониторинга

**Ответ:**

| Система | Модель | Пояснение |
|---|---|---|
| Prometheus | Pull | В основном самостоятельно собирает метрики через HTTP endpoints; для отдельных задач возможен Pushgateway |
| TICK Stack | Push / Pull | Telegraf может как собирать метрики опросом, так и принимать данные, затем отправлять их в InfluxDB |
| Zabbix | Гибридная | Поддерживает пассивные и активные проверки, а также отправку данных через Zabbix Trapper |
| VictoriaMetrics | Гибридная | Поддерживает получение метрик через Pull и приём данных через Push |
| Nagios | Преимущественно Pull | Выполняет активные проверки, но также поддерживает пассивные результаты проверок |

**Вывод:** большинство современных систем мониторинга поддерживают различные механизмы получения метрик. Конкретная модель зависит от используемых компонентов и конфигурации.

### Задание 8. Мониторинг утилизации CPU

**Задача:** построить график использования процессора в Chronograf Data Explorer.

**Выполнение:**

В интерфейсе Chronograf был открыт раздел **Data Explorer**.

Выбраны следующие параметры:

| Параметр | Значение |
|---|---|
| База данных | `telegraf.autogen` |
| Measurement | `cpu` |
| Host | `telegraf-getting-started` |
| Field | `usage_system` |
| Группировка | По времени |
| Интервал наблюдения | Последние 15 минут |

Для отображения метрики использовался запрос InfluxQL:

```sql
SELECT mean("usage_system")
FROM "telegraf"."autogen"."cpu"
WHERE time > now() - 15m
GROUP BY time(10s), "host" fill(null)
```

В результате был получен график загрузки процессора.

### Задание 9. Мониторинг Docker-контейнеров с помощью Telegraf

**Задача:** подключить плагин `inputs.docker` и убедиться, что в InfluxDB появились метрики Docker.

**Выполнение:**

В конфигурационный файл `telegraf-homework.conf` был добавлен плагин:

```toml
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

В Docker Compose для контейнера Telegraf был добавлен доступ к Docker-сокету:

```yaml
volumes:
  - ./telegraf-homework.conf:/etc/telegraf/telegraf.conf:ro
  - /var/run/docker.sock:/var/run/docker.sock:ro
```

При первоначальном запуске возникла ошибка:

```text
permission denied while trying to connect to the Docker daemon socket
```

Причиной стала нехватка прав у процесса Telegraf для доступа к Docker-сокету.

Были проверены права доступа:

```bash
ls -l /var/run/docker.sock
```

В результате установлено, что Docker-сокет принадлежит группе с GID `988`.

Для исправления конфигурации в сервисе Telegraf был указан пользователь и соответствующая группа:

```yaml
user: "telegraf:988"
```

Значение GID соответствует группе Docker на использованной виртуальной машине.

После изменения конфигурации контейнер был пересоздан:

```bash
docker compose -f docker-compose.homework.yml up -d --no-deps --force-recreate telegraf
```

Для проверки поступления метрик выполнен запрос:

```bash
docker compose -f docker-compose.homework.yml exec influxdb \
  influx -database telegraf -execute 'SHOW MEASUREMENTS'
```

В InfluxDB появились измерения:

Это подтверждает успешную работу плагина `inputs.docker`.

Дополнительно в Chronograf Data Explorer был построен график потребления оперативной памяти Docker-контейнерами.

Использовался запрос:
